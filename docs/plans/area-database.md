# Areas: community area and climb database

Status: final for phase 1, decisions from Will's review folded in (2026-09-18).

The feature is called **Areas**.
API routes are `/v1/areas/*` for areas and `/v1/area-climbs/*` for their climbs, shared code lives in `packages/features/src/areas`, and web pages are `/app/areas/:slug` and `/app/climbs/:slug`.
Climbs get their own API prefix because `GET /v1/climbs` and `climbCatalogue` already mean "the climbs this user has logged", and `/v1/areas/climbs/...` would collide with `/v1/areas/:slug`.
The web has no `/app/climbs` route today, so the climb page can take it.

## 1. What exists today

| Concern      | What the repo does                                                                                                                                                                    |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Backend      | One Hono Worker (`packages/api/src/app.ts`), Zod validation at the edge, typed `hono/client` consumed by web and mobile                                                               |
| Database     | Cloudflare D1, which is SQLite. Drizzle schema in `packages/api/src/db/schema.ts`, migrations generated by drizzle-kit, all queries in `lib/repo.ts`                                  |
| Transactions | D1 has no interactive transactions. `db.batch([...])` runs a list of statements as one atomic transaction, and the repo already uses it for multi-table writes                        |
| Auth         | Clerk. Every `/v1/*` route passes one middleware that verifies the Clerk token and sets `userId`. There are no roles; `hasFeature` reads Clerk Billing features only                  |
| Tests        | Vitest in the Workers pool against a real local D1 (`packages/api/test`). The harness signs a request in as whoever the `x-test-user` header names, so a two-user test is two headers |
| Clients      | Web is React Router 7 on Workers; mobile is Expo. Shared hooks and transforms live in `packages/features`, and every string goes through `t()` in four locales                        |

### How climbs and sends are modelled

There is no climb table and no send table.
A session row owns its climbs as a JSON array in `sessions.climbs_json`; each element is `{ name, grade, kind: send|attempt, style, tries, circuit?, wall?, endurance? }`.
A climb's identity is the slug of the name the user typed (`climbSlug`, the same function as `tagSlug`), scoped to that user.
Projects (`projects`) and per-climb notes (`climb_notes`) hang off `(user_id, slug)` and `(user_id, fingerprint, climb_slug)`.
The user's climb list (`GET /v1/climbs`) is computed on read by folding every session's JSON.

The effort engine scores a session from the grades in that JSON, and the persisted RPE, title and top grades are derived from it at write time.

### Gym versus outdoor

`sessions.location` is `indoor | outdoor`.
Indoor sessions may carry `gym_id`, pointing at a gym the user defined themselves (`gyms` is per user, with circuits and walls).
Outdoor sessions have nothing: the crag is whatever the user typed as the session name.
Areas is the outdoor counterpart of `gym_id`.

## 2. Where the brief meets the stack

Three parts of the brief assume Postgres or a send table, and are adapted rather than copied.

1. **No `pg_trgm`, no PostGIS.**
   D1 is SQLite.
   Duplicate suggestions compute trigram similarity in the Worker over a small candidate set pulled by an indexed query (siblings, and a latitude/longitude bounding box for areas).
   The candidate set is tens of rows, so this is cheap and needs no extension.
   Full-text search (SQLite FTS5) is the upgrade if name search over the whole database gets slow; it needs a virtual table Drizzle cannot express, which is why it is not in phase 1.
2. **"Approve in a transaction" becomes a guarded batch.**
   Entities carry a `version` integer.
   Approval reads the entity, runs conflict detection in the Worker, then submits one `db.batch` whose entity `UPDATE` is guarded by `WHERE version = ?`, and whose revision status update is guarded by the entity having reached `version + 1`.
   If another approval landed in between, both statements change zero rows and the API answers 409.
3. **There is nothing to "reassign" on merge, because sends are JSON.**
   Rewriting `climbs_json` across every user who logged a duplicate would be a many-row, many-user write for no gain.
   Instead, a link table records which area climb a logged climb points at (section 3), and a merge is one `UPDATE` on that table.
   There are no comments or list entries in the product today, so there is nothing else to move.

## 3. Schema

All additive.
One Drizzle migration per commit that needs it, generated with `db:generate`, never hand-written.

### `users.role`

`text enum('user', 'moderator', 'admin') not null default 'user'`.

Stored in D1 rather than Clerk metadata: the moderation middleware reads it with one indexed query, tests set it with one insert, and a role change is a `wrangler d1 execute` by Will with no token refresh to wait for.
Admins are moderators who can also create regions and change roles (the role change is a later endpoint; phase 1 sets roles by hand).

### `areas`

| Column           | Type                                     | Notes                                                                                                            |
| ---------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `id`             | text primary key                         | UUID                                                                                                             |
| `parent_id`      | text, nullable                           | Null only for regions                                                                                            |
| `path`           | text not null                            | Materialized path of ancestor ids, `/<region>/<area>/<crag>/<self>/`                                             |
| `depth`          | integer not null                         | `0` is a country region                                                                                          |
| `name`           | text not null                            |                                                                                                                  |
| `name_key`       | text not null                            | `tagSlug(name)`, indexed, for prefix search and exact-duplicate checks                                           |
| `slug`           | text not null unique                     | Stable: set at creation, never changed by a rename (section 4, Slugs)                                            |
| `description`    | text                                     |                                                                                                                  |
| `lat`, `lon`     | real, nullable                           | Required on a user-created top-level area (checked in Zod, not the database, since sectors may leave them empty) |
| `region_code`    | text, nullable, unique                   | ISO 3166 code on seeded regions only (`US`, `US-CA`, `CA-BC`), so the seed is idempotent                         |
| `status`         | `pending \| active \| merged \| deleted` |                                                                                                                  |
| `merged_into_id` | text, nullable                           | Reserved for area merges, which are not in phase 1                                                               |
| `version`        | integer not null default 1               | Bumped by every applied change                                                                                   |
| `created_by`     | text, nullable                           | Nullable so account deletion can anonymise approved content (section 4)                                          |
| timestamps       | `created_at`, `updated_at`               |                                                                                                                  |

Indexes: `parent_id`, `path`, `name_key`, `status`, `lat`.

**Why a materialized path and not a closure table.**
Climbing trees are shallow (rarely deeper than six) and read far more than they are written.
With a path, ancestors are the ids already in the row, fetched with one `WHERE id IN (...)`, and descendants are one indexed range scan `WHERE path >= '/x/y/' AND path < '/x/y0'` (the character after `/` is `0`, so the range covers exactly the subtree).
Re-parenting a subtree is one `UPDATE ... SET path = ? || substr(path, ?)` over that range.
A closure table stores depth-many rows per area, and a move rewrites subtree-times-depth rows; it buys nothing here that a shallow path does not already give.
A recursive CTE over `parent_id` alone also works in SQLite, but walks a level at a time and does not index a subtree.

**Regions.**
Regions are seeded by admins, never created by users: every country (ISO 3166-1), plus US states and Canadian provinces and territories (ISO 3166-2) as children of their country.
ISO codes carry no licensing concern.
The seed is a Drizzle custom migration (`db:generate --custom`, which is data, not a schema change) inserting on `region_code`, so reapplying it is a no-op.
Users may create a top-level area directly under any region, which must carry coordinates, as the brief asks.
The deepest region wins: a crag in California goes under `US-CA`, a crag in France under `FR`.

### `area_climbs`

Named `area_climbs` so the table does not read as "the user's logged climbs".

| Column                                                          | Type                                   | Notes                                                                                                             |
| --------------------------------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `id`                                                            | text primary key                       |                                                                                                                   |
| `area_id`                                                       | text not null                          | Any area except a region                                                                                          |
| `name`, `name_key`, `slug`, `description`                       |                                        | As on `areas`                                                                                                     |
| `type`                                                          | `boulder \| sport \| trad \| top_rope` | `boulder` maps to the boulder discipline, everything else to route. Ice, mixed and aid can be added later         |
| `grade_scale`                                                   | `v \| font \| yds \| french`           | Must match the discipline, same rule as the log form                                                              |
| `grade_value`                                                   | text, nullable                         | Stored as written, parsed with `parseGrade` from `@sendtally/core`. Nullable: an ungraded project is a real thing |
| `length_m`                                                      | integer, nullable                      |                                                                                                                   |
| `bolts`                                                         | integer, nullable                      | Only meaningful for `sport`                                                                                       |
| `first_ascent`                                                  | text, nullable                         | Free text ("Chris Sharma, 2001"); structured first-ascent data is not worth a schema yet                          |
| `status`, `merged_into_id`, `version`, `created_by`, timestamps |                                        | As on `areas`. `merged_into_id` is live for climbs in phase 1                                                     |

Indexes: `area_id`, `name_key`, `status`, `merged_into_id`.

The area climb's grade is the guidebook grade.
A user's logged grade stays in their session JSON and stays what the effort engine scores, so a moderator changing a climb's grade never rescores anyone's history.

### `session_climb_links`

The bridge from a logged climb to an area climb, following the shape `climb_notes` already uses.

| Column        | Type                                              |
| ------------- | ------------------------------------------------- |
| `user_id`     | text not null                                     |
| `fingerprint` | text not null                                     |
| `climb_slug`  | text not null (slug of the name in `climbs_json`) |
| `climb_id`    | text not null                                     |

Primary key `(user_id, fingerprint, climb_slug)`, index on `climb_id`.

- `climbs_json` is untouched, so every existing session, score, note and project keeps working with no data migration.
- A merge is `UPDATE session_climb_links SET climb_id = :keep WHERE climb_id = :dup`.
- A rename of the area climb orphans nothing, because the link key is the slug the user logged, not the area climb's name.
- Deleting a session deletes its links in the same batch that already deletes its notes and tags.

### `sessions.area_id`

Nullable, the outdoor counterpart of `gym_id`, and in phase 1 (Will: the crowdsourcing needs it to be effective).
Choosing a crag for an outdoor session narrows the climb search in the log form, prefills the area when adding a climb, and lets the area page count visits later.
It must be a visible area and not a region; the session edit path validates it like `gym_id`.

### `content_revisions`

| Column                                                                  | Type                                            | Notes                                                                          |
| ----------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------ |
| `id`                                                                    | text primary key                                |                                                                                |
| `entity_type`                                                           | `area \| climb`                                 |                                                                                |
| `entity_id`                                                             | text not null                                   | See the deviation below                                                        |
| `proposed_json`                                                         | text not null                                   | Only the fields the user changed, validated by the same Zod as creation        |
| `base_json`                                                             | text not null                                   | Snapshot of the editable fields, plus `version`, when the draft was last saved |
| `change_summary`                                                        | text                                            |                                                                                |
| `status`                                                                | `pending \| approved \| rejected \| superseded` |                                                                                |
| `submitted_by`, `reviewed_by`, `review_note`, `reviewed_at`, timestamps |                                                 |                                                                                |

Unique partial index on `(submitted_by, entity_type, entity_id) WHERE status = 'pending'`, so the database enforces one draft per user per entity and a re-edit is an upsert on it.
Drizzle expresses partial indexes for SQLite with `.where()`.

**Deviation from the brief:** `entity_id` is never null.
Creations write the entity straight away with status `pending` (the brief's own creation policy), so there is always an id to point at and a creation needs no revision row.
Moderators review pending creations from the entity tables directly.
The creator edits their own pending entity in place, because nobody else can see it yet; once it is active, every change goes through a revision.

**History and rollback.** Approved revisions are never deleted.
The history of an entity is its approved revisions in order, each carrying the before (`base_json`) and after (`proposed_json`), with the creation itself on the entity row.
Rollback is a moderator proposing an older `base_json` as a new revision and approving it, so a rollback is audited like any other change.

**Superseded** is set on every pending revision of an entity when that entity is merged away or deleted.

### `duplicate_reports`

`id, keep_climb_id, duplicate_climb_id, reporter_id, note, status (open | merged | dismissed), reviewed_by, review_note, created_at, reviewed_at`.
Unique partial index on `(duplicate_climb_id, reporter_id) WHERE status = 'open'`.

### `content_reports`

For the "Report issue" menu item on both pages: `id, entity_type, entity_id, reporter_id, body, status (open | resolved), reviewed_by, reviewed_at, created_at`.
One table, free text; moderators act on it by editing or deleting the entity.

## 4. Behaviour

### Visibility

One repo helper decides what a user can see: `status = 'active' OR (status = 'pending' AND created_by = :me)`, plus everything for moderators.
Every Areas read goes through it, and the tests prove a second user gets a 404 on the first user's pending area and climb, and does not find them in search.

### Slugs

Readable and globally unique: `the-mandala`.
On a collision the parent area's slug is appended (`the-mandala-buttermilks`), then a number (`the-mandala-buttermilks-2`).
Slugs are set once at creation and never change, so a rename never breaks a link; a merged climb's slug redirects to the survivor.
Readable slugs matter for the public pages planned for phase 2.

### Duplicate check at creation

`POST /v1/areas/similar` and `POST /v1/area-climbs/similar` return candidates for a name in a place.

- Areas: visible siblings under the same parent, plus visible areas within roughly 2 km when coordinates are given (bounding box on the indexed `lat`, filtered on `lon` in SQL, exact distance in the Worker).
- Climbs: visible climbs in the target area and in its sibling areas, because boulders are often filed under the neighbouring sector.
- Score: Dice coefficient over character trigrams of `name_key`, threshold 0.6, plus any exact `name_key` match. Pure function in `packages/core` with a table-driven test.

The create endpoints run the same check themselves and answer 409 with the candidates unless the body says `confirmedNew: true`.
So the confirmation is enforced by the server, and a client that skips the suggestion step cannot create silent duplicates.

### Suggesting an edit

`PUT /v1/areas/:id/draft` and `PUT /v1/area-climbs/:id/draft` create or replace the caller's pending revision; they never write to the entity.
`GET` returns the caller's draft to prefill the form, `DELETE` withdraws it.
Re-saving refreshes `base_json` to the entity as it is now, so a user who re-edits after someone else's change is diffing against the current state.

### Approving a revision and detecting conflicts

A three-way comparison, field by field, over the fields the revision proposes:

- `base[f] == current[f]`: nobody else touched it, apply.
- `base[f] != current[f]` and `proposed[f] == current[f]`: already applied by someone else, no-op.
- `base[f] != current[f]` and `proposed[f] != current[f]`: conflict.

Any conflict makes approval answer 409 with the conflicting fields and their three values.
The moderator picks a value per field in the review screen and approves again with those picks and the current `version`, which is the resolution.
The comparison is a pure function with its own tests; the guarded batch (section 2) handles the race between two approvals.

A re-parent (`parent_id` or `area_id` changing) is a proposable field; applying it rewrites `path` for the subtree in the same batch.

### Merging duplicate climbs

One `db.batch`:

1. Guard: the survivor is `active` or `pending` and not itself merged; the duplicate is not already merged.
2. `session_climb_links`: repoint `climb_id` from duplicate to survivor.
3. `area_climbs`: duplicate gets `status = 'merged'`, `merged_into_id = survivor`; any climb previously merged into the duplicate is repointed to the survivor, so redirects never chain.
4. `content_revisions`: pending revisions on the duplicate become `superseded`.
5. `duplicate_reports`: every open report naming the duplicate becomes `merged`.

Reading a merged climb by id or slug answers with `redirect: <survivor slug>`, and the web loader turns that into a 301, so old links and search results keep working.
A pending creation can be merged into an existing climb too, which is the natural way to reject a duplicate without losing the creator's send.

Rejecting a pending creation sets `deleted` and removes its links; the creator's session keeps its free-text climb, so nothing they logged is lost.

### Authorization

Moderation lives under `/v1/moderation/*`, mounted after a `requireRole("moderator")` middleware that reads `users.role` and answers 403 for anyone else.
The route handlers never re-check, so there is one place to get right.
The test builds its route list from `app.routes` filtered on the prefix and asserts a 403 for a regular user on every one, so a moderation route added later without the middleware cannot pass CI.

### Account deletion

CLAUDE.md requires account deletion to delete every D1 row for the user; Areas is the one place that rule meets shared content.
Deletion removes the user's pending areas and climbs (and their links), drafts, duplicate reports and issue reports, and their `users` row as today.
Approved areas and climbs stay, with `created_by` set to null, because other people's sends link to them; approved revisions stay with `submitted_by` set to null, so the audit trail keeps its content without the person.
The privacy page gets a line saying so, and CLAUDE.md's Security notes gets the same carve-out.

### Content licence

Contributions to Areas (area and climb text and data) are published under Creative Commons Attribution-ShareAlike 4.0 (CC BY-SA 4.0): anyone may reuse the data with attribution, and anything built from it stays under the same licence.
Will chose Creative Commons; BY-SA 4.0 is the recommended variant, to confirm before the terms change ships.
The terms page gets a contributions clause, and the add and suggest-edit forms say "You're sharing this under CC BY-SA 4.0" beside the submit button.

## 6. UI entry points

Web gets everything; mobile gets the log-form part in phase 1, since that is where people log (Will confirmed the split).
Area and climb pages and moderation are web-only for now.

- **Log-session form, outdoor sessions** (web `ClimbNameField` and the mobile equivalent): a crag picker at the session level, searching Areas by name and nearby; the climb name field then searches Areas climbs (scoped to the crag when one is picked) alongside the user's own history.
  When nothing matches, the last row of the dropdown is always "Add “<typed name>” to Areas", which opens the add-climb sheet prefilled with the name, the grade already on the row, and the crag.
  The crag picker has the same "Add this crag" row, prefilled with the typed name and the device location.
  Each sheet shows "Is it one of these?" candidates before its Save button becomes "Yes, it's new".
  A picked or created climb sets `climbId` on the row; typing a free-text name still works exactly as it does today.
- **Area page** `/app/areas/:slug`: breadcrumb from `path`, child areas, climbs, a pending badge on the creator's own pending items, and a "…" menu with Suggest edits, Add sub-area, Add climb, Report issue.
- **Climb page** `/app/climbs/:slug`: details, the user's own sends of it via links, and a "…" menu with Suggest edits, Report duplicate (search picker for the other climb), Report issue.
- **Session page**: the session's crag links to its area page, and a linked climb's name links to its climb page.
- **Moderation** `/app/moderation`: tabs for Creations, Edits, Duplicates, Reports.
  The Edits tab shows a three-column field diff (Before, Proposed, Now) with conflicting rows highlighted and a per-field picker.
  The nav entry only renders for moderators, but that is convenience; the API is the gate.

Every string goes through `t()` in all four locales.
New analytics events (`area_created`, `area_climb_created`, `area_edit_suggested`, `area_duplicate_reported`, and one per moderation action) are listed on the privacy page, with counts and enum properties only.

## 7. Migration strategy

Every change is additive: new tables, and two nullable or defaulted columns (`users.role`, `sessions.area_id`), plus the region seed.
No existing row is rewritten, `climbs_json` is untouched, and existing sessions simply have no links.

Validation against real data, once, before merging the schema commit:

1. `wrangler d1 export` of production to a file in the scratch directory (never committed).
2. Import it into a fresh local D1 and apply all migrations with `wrangler d1 migrations apply --local`.
3. Compare row counts per table and a checksum of `sessions` (fingerprint, `climbs_json`, `rpe`) before and after.

CI already applies the full migration history to an empty D1 on every pull request, which covers the fresh-database path.

Linking existing free-text outdoor climbs to area climbs is not automatic: we cannot tell which crag "The Mandala" in a session named "Bishop" is.
A later "link your past climbs" screen can suggest matches per user; it is out of scope here.

## 8. Designed for, not built in phase 1

- **Logbook CSV import matching.** The similarity function and the `similar` endpoints are the matching engine. The importer would resolve each row's crag and climb to candidates, let the user confirm in the existing review step, and create pending entities for the rest. Kaya's `location` column (boulder or formation) is the first thing to match.
- **Reputation auto-approval.** Creation status comes from one function, `initialStatus(user)`, which returns `pending` for everyone in phase 1. Trusted users are a change to that function plus a count of approved contributions.
- **Photos and topos.** Would hang off `area_climbs.id` and `areas.id` and go through revisions like any other field.
- **Area merges.** `merged_into_id` exists on `areas`; merging would move child areas and climbs by path rewrite.
- **Public, signed-out area and climb pages for search engines.** This is the ad surface the business plan wants, and Areas is exactly the content it needs. It needs unauthenticated read routes outside `/v1` and server rendering on the web. Phase 2.

## 9. Seed data

No third-party climbing data is seeded.
OpenBeta publishes an open climbing dataset, but its initial United States data came from a 2020 scrape of Mountain Project, which is the source our own constraint rules out; revisit only with a legal read and Will's sign-off.
Region seeding from ISO 3166 codes (section 3) is safe and is part of phase 1.

## 11. Commit plan

Each a separate reviewable commit, tests in the same commit as the code they cover.

1. `feat(api): add areas, area climbs and roles to the schema` - Drizzle tables, `users.role`, `sessions.area_id`, migration, region seed.
2. `feat(core): score name similarity for duplicate suggestions` - trigram Dice function and tests.
3. `feat(api): create and read areas and area climbs` - visibility helper, slugs, similar and create endpoints with the 409, reads with breadcrumb, two-user visibility tests.
4. `feat(api): link logged sessions and climbs to areas` - `areaId` and `climbId` on the session body, links written and returned, send-on-own-pending-climb test.
5. `feat(api): suggest edits as pending revisions` - draft upsert, one-draft-per-user test.
6. `feat(api): moderate creations and revisions` - role middleware, approve and reject, three-way conflict detection, 403-on-every-route test.
7. `feat(api): merge duplicate climbs` - reports, merge batch, links-move test, redirect on read.
8. `feat(api): keep approved area content on account deletion` - anonymise rather than delete, privacy and terms copy.
9. `feat(web): area and climb pages` - pages, menus, create and suggest-edit forms.
10. `feat(web): pick a crag and add a climb from the log form`.
11. `feat(mobile): pick a crag and add a climb from the log form`.
12. `feat(web): moderation queue`.

## Acceptance criteria for phase 1

- Migrations run cleanly against a copy of production data; existing sessions are unchanged.
- A regular user can create an area and a climb, log a send on their pending climb, and propose an edit. Another regular user cannot see the pending entities.
- A regular user calling any moderation route directly gets a 403 (tested across every route).
- A moderator can approve and reject creations and revisions, and merge a duplicate, with all links moving to the kept climb (tested).
- The duplicate-suggestion check fires for near-identical names in the same area.
- Tests cover revision conflict detection, the merge batch, and authorization.
